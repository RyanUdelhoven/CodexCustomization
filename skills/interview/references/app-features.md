# App Features

Choose a useful focus from the request: new capability, component contract, or existing behavior change. Do not require another menu unless the distinction is unclear.

Explore unanswered decisions: who triggers the feature, intended result, happy path, affected existing behavior, permissions, persistence, failure/recovery, and meaningful edge cases. For components, consider inputs, outputs, state ownership, variants, keyboard interaction, and narrow viewports where relevant. Inspect callers before asking about contracts.

Useful questions include: “What should happen when there are no eligible items?” “Should this change affect existing records?” “What concrete example would convince you it works?” Ask only those that expose a real gap in the prompt.

Close with scoped behavior and observable acceptance examples, distinguishing requested behavior from optional future work. Hand implementation and checks to the applicable skills.
